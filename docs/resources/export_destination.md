# kividb_export_destination (Resource)

An S3 bucket in your own AWS account that KDB exports are delivered to. KiviDB
writes into it by assuming a role you create, presenting an external id unique
to this destination. The export stays in KiviDB's storage as well; a copy lands
in your bucket.

```terraform
# A bucket in your own AWS account that KDB exports are delivered to.
resource "kividb_export_destination" "backups" {
  name           = "backups"
  aws_account_id = "123456789012"
  bucket         = "acme-kividb-exports"
  prefix         = "kividb/"
}

# The role KiviDB assumes to write into the bucket, built from the
# destination's own policies (hashicorp/aws provider).
resource "aws_iam_role" "kividb_exports" {
  name               = kividb_export_destination.backups.role_name
  assume_role_policy = kividb_export_destination.backups.trust_policy
}

resource "aws_iam_role_policy" "kividb_exports" {
  role   = aws_iam_role.kividb_exports.id
  name   = "kividb-exports"
  policy = kividb_export_destination.backups.permission_policy
}

# Nothing is delivered until the destination passes verification.
resource "kividb_export_destination_verification" "backups" {
  destination_id = kividb_export_destination.backups.id
  depends_on     = [aws_iam_role_policy.kividb_exports]
}
```

## The three steps

1. **This resource** registers the bucket. KiviDB mints the destination's
   external id and answers with the role's `trust_policy` and
   `permission_policy`, already filled in for this destination.
2. **The role**, in your account, named `role_name`, with `trust_policy` as its
   trust policy and `permission_policy` attached. The example above builds it
   with the `hashicorp/aws` provider.
3. **[`kividb_export_destination_verification`](export_destination_verification.md)**
   has KiviDB assume the role, find the bucket and write a test file. Until that
   passes, nothing is delivered and no database can be pointed at the
   destination.

Creating the destination does not verify it, because it cannot: the role's
trust policy names the external id, which only exists once the destination
does. Verifying inside this resource would fail on every first apply.

## What the role needs

The trust policy lets KiviDB's API role (which verifies) and worker role (which
delivers) assume the role, and only with this destination's external id:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "AWS": ["<KiviDB's API role>", "<KiviDB's worker role>"] },
      "Action": "sts:AssumeRole",
      "Condition": { "StringEquals": { "sts:ExternalId": "<external_id>" } }
    }
  ]
}
```

The permission policy lets it write and complete uploads under the prefix, and
read where the bucket is:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:PutObject", "s3:AbortMultipartUpload", "s3:ListMultipartUploadParts"],
      "Resource": "arn:aws:s3:::<bucket>/<prefix>*"
    },
    { "Effect": "Allow", "Action": ["s3:GetBucketLocation"], "Resource": "arn:aws:s3:::<bucket>" }
  ]
}
```

Use `trust_policy` and `permission_policy` rather than copying these: they carry
the real principals and external id. If the bucket is encrypted with a KMS key
of your own, the role also needs `kms:GenerateDataKey` on that key. No bucket
policy is needed, since the role is a principal of your own account. The role
cannot read, list or delete anything in the bucket.

Verification checks, in order: that the role can be assumed with the external
id (`assume_role`), that it answers from `aws_account_id` (`session_account`),
that the bucket exists and is owned by that account (`bucket`), and that a file
can be written at `<prefix>.kividb-verify` (`write`).

## Changing it replaces it

The API has no way to change a destination, so every argument forces a new one,
with a new external id. The role's trust policy follows when it is built from
`trust_policy`, and the verification and any `kividb_instance_export` pointing
here are replaced in turn. Destroying a destination stops deliveries to it:
databases that used it lose their destination, and their schedules are turned
off.

## Schema

### Required

- `aws_account_id` (String) The 12-digit id of the AWS account the bucket and the role are in.
- `bucket` (String) The bucket's name. It must be owned by `aws_account_id`; verification checks the owner, so a bucket of the same name in another account is refused.
- `name` (String) A name for the destination, as the console shows it. 1 to 80 characters.

### Optional

- `prefix` (String) Where in the bucket exports are written: `""` for the bucket's root, or a path ending in `/`. Defaults to `kividb/`. The role may write only under it.
- `role_name` (String) The name of the role KiviDB assumes. It must start with `KiviDBManagement-Exports`. Defaults to `KiviDBManagement-Exports-` and the first 8 characters of the destination's id. Role names are unique within an AWS account, so two destinations in one account need two roles.

### Read-Only

- `bucket_region` (String) The bucket's region, found by verification. Null until then.
- `cloud` (String) Always `aws`: exports are delivered only to S3 for now.
- `created_at` (String) When the destination was created.
- `external_id` (String) The external id KiviDB presents when it assumes the role, unique to this destination. It is what stops another KiviDB organization naming your bucket. Already part of `trust_policy`.
- `id` (String) Destination id. Pass it to `kividb_instance_export.export_destination_id`.
- `last_error` (String) Why the last verification failed, as the API reported it. Null once verified.
- `permission_policy` (String) The role's permission policy, as JSON: write and complete uploads under `bucket`/`prefix`, and read the bucket's location. Attach it to the role. If the bucket is encrypted with a KMS key of your own, the role also needs `kms:GenerateDataKey` on that key.
- `role_arn` (String) The ARN of the role KiviDB assumes: `role_name` in `aws_account_id`.
- `status` (String) `pending` until verified, `verified` once KiviDB has written a test file under the prefix, or `failed` with the reason in `last_error`. Only a verified destination receives exports.
- `trust_policy` (String) The role's trust policy, as JSON: KiviDB's API and worker roles may assume it, only with `external_id`. Use it as the role's `assume_role_policy`.
- `verified_at` (String) When the destination last passed verification.

## Import

Import is supported using the following syntax:

```shell
# An export destination is imported by its id.
terraform import kividb_export_destination.backups 3e7a1c2b-4d5f-4a6b-8c9d-0e1f2a3b4c5d
```
