# Changelog

## 0.6.1 (October 27, 2026)

### Added

- `kividb_instance.reserve_months`: months of credit (0-12) to set aside for
  the database when it is created, as checkout's "Reserve credits" does. It
  is used only at create; afterwards, manage reservations with
  `kividb_credit_reservation`.

### Changed

- Sharded databases (`shard_count` above 1) are available in AWS us-east-1
  and us-west-2. A sharded database must set `reserve_months` to at least 1,
  because it cannot be stopped when the balance runs out. The API refuses one
  without it, and refuses one in a region that cannot build it, with the
  reason.

## 0.6.0 (October 25, 2026)

Most of what KiviDB Cloud has gained since 0.5.0 can now be managed from
Terraform: database users and network access, backups to your own bucket,
alerts, credit reservations, data integration and the AI features. Connecting
a cloud account, API keys, organization members and turning the audit log on
or off stay in the console: the API does not accept API keys for them, on
purpose.

### Added

Databases:

- `kividb_database_user`: ACL users on a database, with a `read_write`,
  `read_only` or `pubsub` profile. The password is given, or generated by the
  API and readable from state; changing `rotation_trigger` generates a new one.
  Import with `<instance_id>/<username>`.
- `kividb_instance_network`: a database's allowlist, the addresses that may
  connect over its public endpoint, each with an optional label. The
  allowlist is the whole list. Destroying the resource leaves the allowlist as
  it is.
- `kividb_private_link`: private connectivity to a database (AWS PrivateLink,
  Azure Private Link Service or Google Cloud Private Service Connect), a paid
  add-on of $25 a month. Sets who may connect, waits for the endpoint service
  and reports `service_name`, and with `public_access_blocked` closes the
  public endpoint. Destroying it opens public access again, to the
  allowlist, and turns private connectivity off.
- `kividb_maintenance_window`: the weekly four-hour window for planned
  maintenance, by day, hour and IANA time zone. Destroying it restores Sunday
  03:00 UTC.
- `kividb_snapshot_schedule`: scheduled disk snapshots, hourly, daily or
  weekly, kept by count (`keep_last`) or by age (`keep_days`). Destroying it
  turns the schedule off and leaves retention as it is.
- `kividb_instance.free_tier`, `shard_count`, `replication_tls`,
  `client_cert_mode` and `client_ca_pem`. The last three are applied by a
  rolling restart, on a new database once it is running.
- `kividb_tls_ca_certificate` and `kividb_client_certificates` data sources.

Backups:

- `kividb_export_destination`: an S3 bucket in your own AWS account that KDB
  exports are delivered to. It returns the role's `trust_policy`,
  `permission_policy`, `role_name` and `external_id`, so the role can be built
  in the same configuration.
- `kividb_export_destination_verification`: verifies a destination (assume the
  role with its external id, check the account and the bucket's owner, write a
  test file under the prefix), retrying for up to five minutes while IAM
  propagates. A destination that does not pass fails the apply with the API's
  reason, and stays in state with `status = "failed"` and `last_error`.
- `kividb_instance_export`: which destination a database's KDB exports are
  delivered to, and whether it exports on its own `daily` or `weekly`.
  Destroying it turns exports off.
- `kividb_kdb_snapshot`: an on-demand KDB export, waited for until written,
  delivered to the database's destination unless `deliver = false`.
- `kividb_kdb_snapshots` and `kividb_disk_snapshots` data sources: list a
  database's or the organization's snapshots, to restore one with
  `kividb_instance.restore_from_kdb_snapshot_id` or `restore_from_snapshot_id`.

Alerts and governance:

- `kividb_alert_channel`: where alerts are delivered -- email to the
  organization's members by role, Slack, Microsoft Teams, PagerDuty or a
  signed webhook. A channel cannot be edited, so any change replaces it; give
  channels `lifecycle { create_before_destroy = true }` so alerts move to the
  new channel before the old one is removed. `url` and `routing_key` are
  sensitive, and a webhook's `signing_secret`, shown once, is kept in state.
- `kividb_alert_rule`: an alert on a database's memory, operations per
  second, p99 latency, connected clients, replication lag or failovers, or on
  the organization's credit runway, sent to one or more channels. `op`,
  `threshold` and `for_minutes` default to the metric's own defaults.
- `kividb_audit_log_settings` data source: whether the organization keeps an
  audit log, and for how long. Read-only: the log is turned on or off by the
  organization's owner in the console.

Credit:

- `kividb_credit_reservation`: set part of the organization's credit aside
  for one database. Nothing is spent or added; other databases see the
  balance less what is reserved, and when that runs out the databases without
  a reservation are stopped first. `terraform plan` checks the reservation
  with the API: a refusal (more than is unreserved, or leaving the other
  running databases less than a day of credit) fails the plan in the API's
  words, and databases left without a reservation are named in a warning with
  the unreserved balance and how many days it lasts, before and after. Set
  `months` (priced once, when set aside) or `amount_cents`. Raising either
  adds the difference in place; lowering replaces the reservation, and the
  plan says what that returns and sets aside. `active` deactivates and
  re-activates it. Destroy deactivates and deletes. Import by id. Owner or
  admin API keys only.
- `kividb_credit_reservations` data source: the balance, reserved and
  unreserved cents, and every reservation.

Data integration:

- `kividb_data_pipeline`: data integration from a PostgreSQL or MySQL
  database into a KiviDB database, first as a snapshot and then change by
  change. Tables map to hash or JSON keys through a key template such as
  `customer:{id}`, with optional `columns`, `rename` and `ttl_seconds`.
  `enabled` starts and stops the pipeline; `resnapshot_trigger` copies every
  table again. `source_password` is write-only on the API side and is kept from
  the configuration. A destroy that cannot drop the PostgreSQL replication slot
  fails with the API's explanation; `force_delete = true` deletes anyway and
  KiviDB keeps trying to drop the slot for about four days. A pipeline is
  billed at $0.04 an hour while it runs plus $0.10 per GB written beyond
  10 GB a month, and starting one needs organization credit for about a month
  of it. Import by name.

AI features:

- `kividb_semantic_cache`: a semantic cache namespace on a database, with its
  embedding provider (`none`, `openai` or `openai_compatible`), `dimensions`,
  `threshold` and `default_ttl_seconds`. Destroying it deletes every cached
  entry. `dimensions` changes in place only while the namespace is empty.
- `kividb_agent_memory_store`: an agent memory store on a database, with its
  embedding and language models, session and memory TTLs, summarizing and
  extraction settings, custom memory types and PII redaction. Destroying it
  deletes every session and memory in it. Not available on sharded databases.
- `kividb_context_model`: a Context Retriever model over a database's records,
  its entities, fields and relationships written as nested attributes. Each
  apply rebuilds its indexes; destroying it deletes the model, its indexes and
  its agent keys, and leaves the records. Exposes `tools` and `mcp_url`.
- `kividb_context_agent_key`: an agent key for a context model, optionally
  limited to some entities and fixed filters. The key is shown once and kept
  in state as the sensitive `key`; any change makes a new key and revokes the
  old one, and a key revoked elsewhere leaves state on refresh.

### Changed

- `kividb_instance.tls_only` changes in place, without a restart, instead of
  replacing the database. It needs `tls_enabled`, and it is ordered against
  `tls_enabled` and `client_cert_mode` changes in the same apply.
- `kividb_instance.aof_enabled` no longer defaults to `true`; it is planned
  from the tier (on for paid, off for the free tier), which is what the API
  does. Setting the other value is refused at plan instead of failing the
  apply as an inconsistent result.
- A refusal that carries only field errors (a 400 from the API's validation)
  now names each field and what is wrong with it, instead of `bad_request
  (HTTP 400)`.

## 0.5.0 (October 8, 2026)

### Added

- Azure subscriptions as cloud accounts. `kividb_cloud_account` and
  `kividb_cloud_accounts` read Azure connections and report
  `azure_tenant_id`, `azure_subscription_id`, `azure_resource_group`,
  `azure_snapshot_account` and `azure_snapshot_container` (null for AWS
  accounts and Google Cloud projects). A `kividb_instance` with
  `cloud = "azure"` can run in one through `cloud_account_id`.
- `kividb_instance.restore_from_snapshot_id` and
  `kividb_instance.restore_from_kdb_snapshot_id`: create a database from a disk
  snapshot or a KDB snapshot. A snapshot is restored only in its own cloud,
  region and cloud account. When the snapshot's id is known at plan time, the
  plan shows the account the database will be placed in and refuses a
  different cloud, region or account; otherwise the API refuses it at apply,
  and the error names the value to set.
- `cloud_account_name` on `kividb_instance` and the `kividb_instance` data
  source: the connected account's name as the console shows it.
- `cloud_account_id` and `cloud_account_name` on `kividb_disk_snapshot`: the
  account the snapshot is stored in, and the only one it can be restored into.

### Changed

- `kividb_instance.cloud_account_id` is now optional and computed. Left unset
  on a database created from a snapshot, it is the snapshot's account. Left
  unset on any other new database, it is still KiviDB's cloud. Removing it from
  the configuration of an existing database no longer plans a replacement into
  KiviDB's cloud: the database stays in the account it is in. Setting it to a
  different account still replaces the database, and the same id written in a
  different case no longer does.
- The cloud account `status` is documented as `verified`, `pending` or
  `broken`, which is what the API reports.
